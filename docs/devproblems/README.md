# 开发问题记录

这里记录重构、实现和评审中实际发现的问题与决策难点。目的不是替代 issue tracker，而是沉淀可跨项目阶段汇总的工程经验：哪些问题反复出现、根因属于哪个层、什么修复方式有效、哪些方案因缺少真实需求而暂缓。

## 记录原则

- 只记录已由代码、测试、线上现象或评审核实的问题；“可能的长期演进”要明确标为条件性议题。
- 每项带稳定 `DP-` 编号、分类、严重度、状态和标签，便于后续按类别统计。
- 将“事实”“影响”“修复方向”“验证条件”分开写，避免把方案假设当成现状事实。
- 对被后续评审核正的描述保留更正记录，防止错误结论再次进入实施计划。

## 分类建议

| 分类 | 说明 |
| --- | --- |
| `runtime-control` | run 生命周期、取消、调度、事件状态机 |
| `context-compaction` | context 预算、压缩、prompt cache、消息边界 |
| `persistence-recovery` | 落盘、一致性、resume、分支、checkpoint |
| `tool-contract` | 工具输入、生命周期、并发、审批与副作用 |
| `observability` | 日志、事件、成本、审计、排障信号 |
| `architecture-scope` | 架构边界、ROI、过度设计、分期决策 |
| `testing-review` | fixture、回归覆盖、评审过程与证据核验 |

## 文件命名

按主题建立文件：`YYYY-MM-<topic>.md`。每个文件可以记录多个相关 `DP-`，但每项必须独立编号。

后续汇总时可按 frontmatter/表格中的分类、标签、状态统计，不需要从叙述文本反推。
